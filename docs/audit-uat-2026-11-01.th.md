## 1. Pipeline โดยย่อ

```
LINE ─POST /api/line/webhooks─▶ LineSignatureGuard (HMAC raw body)
  └▶ LineWebhookAdapter: zod parse, ingress limit 100 events/s (เกิน → 503), queue.add(jobId = webhookEventId)
BullMQ "line-events" (concurrency 10, limiter 12 jobs/s ทั้งคิว)  ── retry: "line-events-retry" (3, backoff)
  └▶ LineEventsProcessor: ต่อคิวต่อ user ใน memory → ban/burst/hourly/spam → claimWebhookEvent (DB lease 120s)
      └▶ MessageProcessorService
          findDelivery(webhookEventId) ─ มีแล้ว → deliver ซ้ำ (ไม่เรียก AI)
          saveIncomingEvent (tx: conversation upsert + unread +1 + USER history; dedup ด้วย lineMessageId)
          context.load (Redis) → ChatbotService (rule / intent / RAG / AI)
             AI ทุก call: AiBudgetService (Redis 30 calls/s รวมทุกคน) → reserve credit (tx) → provider → settle (tx)
          saveReply (tx: เช็ค lease + LineDelivery upsert key = webhookEventId)
          LineDeliveryService.deliver: REPLY ถ้า token ยังไม่หมดอายุ (event ts + 50s) และ reply limit 30/s ผ่าน
             ไม่งั้น PUSH (retry key, กิน quota) → ACCEPTED → finalize (history + context)
recovery: webhook ทุก 15s (20 แถว), delivery ทุก 5s (20 แถว)
```

จำนวน AI call ต่อ turn ที่วัดได้ (เส้นทาง low-confidence ซึ่งหนักที่สุด): embedding 1 + classifier 1 + answer 1
= **~2.6 billed call/turn** (เฉลี่ยรวม postback/sticker ที่ไม่ใช้ AI) → reserve + settle = **~5 tx บนแถว wallet เดียวกันต่อ turn**

## 2. สิ่งที่พบ

ระดับ: **H** = กระทบลูกค้า/เงินเมื่อโหลดจริง, **M** = เกิดในสถานการณ์เฉพาะ, **L** = ปรับปรุง
หลักฐาน: **[วัด]** = ยืนยันด้วย load test, **[โค้ด]** = จากการอ่านโค้ด ยังไม่ได้ reproduce

### H1. ค่า worker ปัจจุบันรับได้แค่ ~3 แชท/วินาที แชทที่เกินกลายเป็น PUSH และรอเป็นนาที [วัด]

- **จุด:** `line-events.queue.ts` (`LINE_EVENTS_CONCURRENCY` 10, limiter 12 jobs/s), `line-channel.adapter.ts:224`
  (`replyUntil = event.timestamp + 50s`), `line-delivery.service.ts:115-132`
- **กลไก:** throughput ≤ min(limiter, concurrency ÷ เวลาต่อ turn) เวลาต่อ turn ที่ AI ตอบ ~3.5s → 10 ÷ 3.5 ≈ **2.9 turn/s**
  เกินจากนั้นต่อคิว เมื่อรอเกิน 50s นับจาก LINE ส่ง event, reply token หมด → ส่ง PUSH (นับ quota ข้อความของ OA)
- **หลักฐาน:** 30 แชท/s × 60s (ค่า default): ทำได้ ~2.7 turn/s, **PUSH 92%**, p50 4.8 นาที, ช้าสุด 9.7 นาที, drain 10 นาที
  แม้แค่ 5 แชท/s ก็ p50 26s และ PUSH 3% · 50 คนพร้อมกัน: ตอบครบด้วย REPLY แต่คนท้าย ๆ รอ 22s
- **Postgres ไม่ใช่คอขวดในรอบนี้:** conn สูงสุด 12, ~109 tx/s, CPU PG ~6%
- **แก้:** ตั้ง `LINE_EVENTS_CONCURRENCY` ≈ เป้าแชท/s × เวลาต่อ turn × 1.3 และ limiter ≥ 2× เป้าแชท/s (ค่าที่วัดแล้วอยู่หัวข้อ 5)
  เป็นการตั้ง env ที่ diff ปัจจุบันรองรับแล้ว ไม่ต้องแก้โค้ด

### H2. AI rate limit รวม 30 call/s ทำให้ลูกค้าได้ข้อความ fallback และห้องถูกส่งต่อแอดมินทั้งที่แค่โหลดสูง [วัด]

- **จุด:** `usage/rate-limit/ai-budget.service.ts:30-44` (`AI_GLOBAL_LIMIT_PER_SEC` 30, นับทุก call: embedding,
  classifier, answer), `answer.service.ts:220,328`, `chatbot.service.ts:373-376` → `user-session.service.ts:127`
- **กลไก:** 1 แชทใช้ ~2.6 call → 30 call/s รับได้แค่ ~11 แชท/s เมื่อเกิน call ถูกปฏิเสธ → `isFallback` → ตอบ fallback +
  `requestAdmin` → ห้องเป็น `waiting_admin` + แจ้งเตือนแอดมิน (embedding ที่ถูกปฏิเสธโยน `ServiceUnavailableException`)
- **หลักฐาน:** 30 แชท/s, concurrency 150, ค่า AI default: **2,323/3,601 ข้อความ (65%) ได้ fallback,
  988/1,000 ห้องเป็น `waiting_admin`**, log `AI budget exceeded (global)` 2,323 ครั้ง · ตั้ง 150 แล้ว fallback = 0
- **ผลกระทบ:** ตอนคนทักเยอะ แอดมินจะเจอห้อง "ขอแอดมิน" ท่วม inbox ทั้งที่ AI ตอบได้ ลูกค้าได้ "ขอให้เจ้าหน้าที่ช่วยตรวจสอบ"
- **แก้:** (ก) ตั้ง `AI_GLOBAL_LIMIT_PER_SEC` ≥ เป้าแชท/s × 3 และไม่เกิน RPM ของ provider ÷ 60
  (ข) ระยะยาว: เมื่อ budget global เต็ม ให้รอ/หน่วงหรือส่งเข้า retry queue แทนการตอบ fallback และ**ไม่ requestAdmin**
  เพราะไม่ใช่เหตุที่ต้องการคน

### H3. ลำดับต่อ user เป็น lock ใน memory และกิน worker slot [วัด บางส่วน]

- **จุด:** `line-events.processor.ts:56,130-152` (`userProcessingTails`)
- **กลไก:** ข้อความถัดไปของ user เดียวกันรอ Promise ของข้อความก่อนหน้า **โดยถือ worker slot ไว้** และใช้ได้แค่ใน process เดียว
  (ผิด `.claude/rules/line-delivery.md` "in-memory locks are not enough"; ตรงกับ P1-07 ใน `chatbot-core-rag-audit-2026-10-01.th.md`)
- **หลักฐาน:** 20 คน × 5 ข้อความรัว: ลำดับถูก (0 violation, 1 instance) แต่ **p50 47s, ช้าสุด 95s, PUSH 46%** —
  slot ถูกใช้รอคิวของคนเดิม ส่วน multi-instance ยังไม่ได้วัด (ตอนนี้ deploy instance เดียว)
- **แก้:** ก่อน scale >1 instance ต้องมี lock ต่อ user ใน Redis/DB (หรือ BullMQ group/partition ตาม userId);
  ระยะสั้น: จำกัดจำนวน slot ที่ user เดียวถือได้ หรือ re-queue แบบ delayed แทนการรอใน slot

### M1. reply limit 30/s เต็มแล้วตกไป PUSH ทันที (ทิ้ง reply token ที่ยังใช้ได้) [วัด]

- **จุด:** `line-reply.service.ts:168-179` คืน `false` → `line-delivery.service.ts:122-132` ไปทาง PUSH;
  log เขียนว่า "dropping reply" แต่จริง ๆ ส่ง PUSH
- **หลักฐาน:** 30 แชท/s: PUSH 265–343 ข้อความ / 2 นาที (7–10%) ทั้งที่ token ยังไม่หมดอายุ ตั้ง `LINE_GLOBAL_REPLY_LIMIT_PER_SEC`=100 แล้ว PUSH = 0
- **แก้:** ตั้ง limit ให้สูงกว่าเป้า (LINE reply API รับได้สูงกว่ามาก) และในโค้ด: รอ window ถัดไปสั้น ๆ ก่อนตกไป PUSH ตราบที่ `replyUntil` ยังไม่ผ่าน; แก้ข้อความ log

### M2. Postback ที่ถูก retry ถูกบันทึกซ้ำทุกครั้ง และ unread บวกซ้ำ [วัด]

- **จุด:** `line-channel.adapter.ts:251-263` dedup ด้วย `lineMessageId` เท่านั้น; postback (`:441-449`) ไม่มี id
- **หลักฐาน:** crash test: postback 4 รายการถูกบันทึก **5 แถวต่อรายการ** (1 ต่อ attempt) และ `unreadCount` = 5
- **แก้:** ใช้ `webhookEventId` เป็น key dedup ของ incoming (เช่นเก็บใน column unique หรือ upsert ด้วย key นี้) สำหรับทุก event ที่ไม่มี message id

### M3. worker ตายกลาง AI call → reservation ค้าง HELD → turn FAILED, เครดิตถูกกันไว้ [วัด]

- **จุด:** `credit.service.ts:207-210` (`existing.status !== 'RELEASED'` → `PendingAiUsageError`), reservation หมดอายุ 120s
  แต่ถูกเปลี่ยนเป็น `UNKNOWN` เฉพาะตอนแอดมินเปิดรายการ (`listUnresolvedReservations`)
- **หลักฐาน:** crash test (SIGKILL ระหว่าง 10 แชท/s): **31 turn FAILED หลัง 5 attempts** (`PendingAiUsageError`), ลูกค้าไม่ได้คำตอบ,
  **31 reservation ค้าง HELD, `reservedCredit` ค้าง 10.17 credit**, provider call ที่ไม่ถูกบิล 1 ครั้ง (R1 เดิม)
- **ข้อดีที่ยืนยันได้:** ไม่มีการตัดเงินซ้ำ ไม่มี DEBIT เกิน ยอดอื่นตรงหมด
- **แก้:** job สำหรับ HELD ที่เลย `expiresAt` → `UNKNOWN` อัตโนมัติ + alert; ตัดสินใจ policy ว่า turn ที่ค้าง pending ควรตอบลูกค้าว่าอะไร
  (ตอนนี้เงียบ); การ release อัตโนมัติต้องระวังเพราะ provider อาจตอบไปแล้ว (เหตุผลเดิมใน `credit.service.ts:517`)

### M4. DEBUG log เปิดใน production: 9 MiB/นาที ที่ 30 แชท/s [วัด]

- **จุด:** `main.ts` สร้าง `new AppLogger({ timestamp: true })` ไม่กำหนด `logLevels` → debug/verbose ออกทั้งหมด
- **หลักฐาน:** 10 นาทีที่ 30 แชท/s: log 92 MiB / 1.8 ล้านบรรทัด (ส่วนใหญ่ DEBUG ของ router/retrieval)
  ปิด debug แล้ว log เหลือ 2.4 MiB/10 นาที (ลด ~40 เท่า) แต่ CPU ของ Node ที่ 30 แชท/s ยังเต็ม core เท่าเดิม —
  log ไม่ใช่สาเหตุหลักของ CPU (ดูหัวข้อ 4)
- **ผลกระทบ:** CPU ของ Node (thread เดียว) และดิสก์ VPS (~13 GB/วันถ้าโหลดคงที่ 30/s; docker json log ไม่ rotate ถ้าไม่ตั้ง)
- **แก้:** อ่าน `LOG_LEVEL` จาก env (production = log/warn/error) และตั้ง log rotation ของ docker

### M5. ตัวนับ abuse/rate limit ถูกนับก่อน claim [โค้ด]

- **จุด:** `line-events.processor.ts:161-209` · redelivery ภายใน ~1 ชม. ถูก BullMQ dedup ด้วย jobId (ทดสอบ redelivery 20%: ไม่ซ้ำ)
  แต่ `removeOnComplete.count` 5,000 ที่ 30 แชท/s เก็บ job ได้แค่ ~3 นาที → redelivery หลังนั้นถูกนับ burst/hourly/spam
  อีกรอบ (อาจได้ strike) ก่อนถูก claim ปัดตก
- **แก้:** เช็ค `processedLineWebhookEvent` ก่อน consume limit หรือเพิ่ม count ของ removeOnComplete

### M6. Ingress 100 events/s → 503, และช่วงแอปล่มข้อความหาย ถ้าไม่ได้เปิด redelivery [วัด บางส่วน]

- **จุด:** `line-webhook.adapter.ts` (`LINE_GLOBAL_INGRESS_LIMIT_PER_SEC`)
- **หลักฐาน:** crash test: ระหว่างแอปล่ม 5s webhook 65 รายการต่อไม่ติด — ใน production LINE จะส่งซ้ำก็ต่อเมื่อเปิด
  "Webhook redelivery" ใน LINE Developers console
- **แก้:** เปิด redelivery ใน console (เช็คตอน UAT) และวาง reverse proxy ให้คืน 5xx (ไม่ใช่ timeout ค้าง) ตอน restart

### M7. AI limit ต่อ user 60 call/ชม. = ตอบด้วย AI ได้แค่ ~22 ข้อความ/ชม. แล้วตกเป็นห้องขอแอดมิน [โค้ด + คำนวณ]

- **จุด:** `ai-budget.service.ts` (`AI_USER_LIMIT_PER_HOUR` 60 นับเป็น **call** ไม่ใช่ข้อความ) เทียบ
  `LINE_USER_HOURLY_LIMIT` 60 **ข้อความ** · วัดได้ ~2.7 call/ข้อความ → ข้อความที่ ~23 ในชั่วโมงได้ fallback + `requestAdmin` (เส้นทางเดียวกับ H2)
- **หลักฐาน:** ในการทดสอบแต่ละ user ส่ง ≤ 18 ข้อความ/10 นาที จึงไม่ชน (ตั้งใจหลบ) ยังไม่ได้รันกรณีชน
- **แก้:** ตั้ง `AI_USER_LIMIT_PER_HOUR` ≈ `LINE_USER_HOURLY_LIMIT` × 3 หรือเปลี่ยนให้นับต่อ turn; และเช่นเดียวกับ H2 —
  budget เต็มไม่ควรส่งห้องไปหาแอดมิน

## 3. จุดที่ตรวจแล้วถูกต้อง

ยืนยันด้วย load test ทุกรอบ (16 รอบ รวม 66,433 event, 170,147 billed AI call):

- **Billing ถูกต้องทุกรอบ:** provider call = `aiUsageEvents` (ไม่มี call หลุดบิล ยกเว้น crash 1 ครั้งตาม M3) ·
  usage ที่คิดเงินมี DEBIT ตรง 1 แถวทุกแถว · Σ DEBIT = Σ `chargedCredit` = ยอด wallet ที่ลด = `lifetimeSpentCredit` ที่เพิ่ม ·
  DEBIT ติดลบทุกแถว · `reservedCredit` ของ wallet และ budget กลับเป็น 0 หลัง drain · reservation เป็น SETTLED ทั้งหมด ·
  ไม่มี deadlock (ล็อกเรียง reservation → wallet → budget ทุกเส้นทาง)
- **Webhook idempotency:** ทุก event ถูก claim ครั้งเดียว `COMPLETED` attempt 1 · redelivery 20% ไม่เกิด USER row ซ้ำหรือคำตอบซ้ำ
- **Incoming dedup ด้วย `lineMessageId`:** ข้อความ text/sticker ไม่ซ้ำแม้หลัง crash · `unreadCount` = จำนวน USER row ทุกห้อง
- **Delivery:** ไม่มี REPLY token ถูกใช้ซ้ำ (fake LINE ปฏิเสธ token ซ้ำ/หมดอายุ — ตัวนับเป็น 0) ·
  PUSH ใช้ retry key ไม่ส่งซ้ำ · ACCEPTED → finalize ครบ (ไม่มี `finalizedAt` ค้าง)
- **ลำดับต่อ user (instance เดียว):** 0 violation ทุกรอบ รวม 5 ข้อความรัว
- **Ingress:** p95 ≤ 33ms ที่ 30 แชท/s (ตอบ LINE เร็ว ไม่รอ AI)
- **Security ที่เกี่ยว (จากโค้ด):** signature ตรวจบน raw body ก่อน parse · ข้อความลูกค้าที่ log ผ่าน `logSafeText` ·
  เส้นทางตอบลูกค้าไม่ส่ง `costThb` หรือ error ดิบ (error ของ AI ถูกแปลงเป็น fallback)

### 4.5 สรุปความจุ

- **คอขวดลำดับแรกคือค่า config** (H1, H2, M1) ไม่ใช่ฮาร์ดแวร์ แก้ด้วย env ได้ทันที
- หลังตั้งค่าแล้ว **คอขวดถัดไปคือ CPU ของ Node (thread เดียว)**: ~20 แชท/s ใช้ ~55% ของ core, ~30 แชท/s เต็ม core
  ผลที่ 30/s จึงแกว่งระหว่าง p95 5s กับ 24s แต่ยังตอบทันใน reply window (≤28s < 50s) ทุกข้อความ
- **Postgres ยังเหลือ** ที่ pool 10; เพิ่ม pool ไม่ช่วย กลับเพิ่ม lock wait และ CPU ของ PG
- AI จริงจะใช้ CPU ฝั่ง Node มากกว่าของจำลอง (HTTPS/TLS, parse response) → ความจุจริงน่าจะต่ำกว่าที่วัดได้

### 5.2 Postgres บนเครื่อง 2 vCPU / 2 GB ร่วมกับ Node + Redis

## 7. สิ่งที่ยังไม่ได้ยืนยัน / ข้อจำกัดของการทดสอบ

- **AI จำลอง:** เวลาตอบเป็นช่วงที่ตั้งไว้ ไม่ใช่ของ provider จริง; ไม่วัด RPM/TPM limit, 429, timeout จริงของ provider
- **Embedding จำลองไม่ตรงกับ vector ในฐานข้อมูล** → ทุกคำถามไปเส้นทาง low-confidence (embedding → classifier → คำตอบ)
  ไม่ได้วัดเส้นทาง grounded knowledge / product RAG / registration ภายใต้โหลด (จำนวน call ใกล้เคียงกัน แต่ query ต่างกัน)
- **รูปภาพ** ไม่อยู่ใน mix (ดาวน์โหลด + vision ใช้ CPU/RAM มากกว่า)
- **Multi-instance ไม่ได้ทดสอบ** — H3 คาดว่าลำดับพัง แต่ยังไม่ได้วัด
- **เครื่อง local ไม่ใช่ VPS จริง:** จำกัด CPU ด้วย cgroup/taskset; I/O ดิสก์และ network ต่างจริง; Node กับ PG ไม่ได้แย่ง core เดียวกันจริง
  ผลที่ 30 แชท/s แกว่งระหว่างรอบ (t3/p1 vs t4/f2) เพราะอยู่ที่ขอบความจุของ core
- **Fake ใช้ CPU เองเล็กน้อย** (timer, JSON, Redis INCR) อยู่ใน process เดียวกับแอป
- ข้อมูลสะสมระหว่างรอบ (ตาราง history/delivery โตขึ้น ~66k แถว) ไม่ได้ reset ระหว่างรอบ
- **ไม่ได้ทดสอบ:** wallet ใกล้หมดระหว่างโหลด (ครอบคลุมแล้วโดย repro F/G ใน `investigation-credit-wallet-contention.md`),
  admin ส่งข้อความระหว่างโหลด, การชน M5/M7, การ profile CPU ของ Node (แนะนำ `--cpu-prof` รอบถัดไปเพื่อหาว่า CPU ไปที่ Prisma/retrieval/BullMQ ส่วนไหน)
- 13 error ของ `bunx tsc --noEmit` มีอยู่ก่อนแล้วใน `test/audit/product-ecom.fixture.ts` และ spec 2 ไฟล์ ไม่เกี่ยวกับงานนี้
