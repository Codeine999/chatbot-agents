# สรุปว่าแก้บอทอะไรไปบ้าง

จัดทำ 29 กันยายน 2026; อัปเดตพฤติกรรม live-data guard วันที่ 30 กันยายน 2026

**มีการแก้สองรอบ:** รอบแรกแก้บั๊กที่ทำให้คำตอบถูกทิ้ง ส่วนรอบสองเปลี่ยนวิธีเลือกข้อมูลและเส้นทางตอบด้วย จึงมีผลมากกว่าการแก้ `ref` อย่างเดียว

## 1. ปัญหาตั้งต้นคืออะไร

ผลทดสอบเดิมมีข้อความตอบ fallback 42 จาก 55 ครั้ง หรือ 76.4% **เฉพาะชุดคำถาม audit ที่รันกับ working tree วันที่ 27 กันยายน** ซึ่งมีตัวตรวจ JSON/รหัสอ้างอิงแล้ว ไม่ใช่สถิติลูกค้าจริง และยังไม่ทราบว่าเป็นโค้ดรุ่นเดียวกับที่ผู้ใช้ทดสอบหรือไม่

ในนั้น 33 ครั้ง โมเดลอ้างรหัสข้อมูลที่ค้นเจอจริง แต่โค้ดรับรหัสคนละรูปแบบ จึงทิ้งคำตอบ อีก 9 ครั้งมาจากข้อมูลไม่พอ ไม่อ้างหลักฐาน หรือ provider ล้มเหลว

**ทำไมตอนทดสอบเองอาจตอบจาก DB ได้ปกติ:**

- โค้ดใน commit `f14a47c` วันที่ 24 กันยายน คืนข้อความจากโมเดลโดยยังไม่มีตัวตรวจ `evidenceIds` จึงไม่เกิดการทิ้งคำตอบด้วยบั๊กรหัสอ้างอิงนี้ในรุ่นนั้น ส่วน audit ระบุว่าทดสอบโค้ดที่ยังไม่ commit จึงใช้ชื่อ commit อย่างเดียวแทนรุ่นที่ทดสอบไม่ได้
- การตอบจาก DB มีทั้ง DIRECT (คืนคำตอบที่จัดไว้โดยตรง) และ RAG (ให้ AI เรียบเรียงจาก DB) บั๊กรหัสอ้างอิงกระทบทาง RAG ในรุ่นที่ audit ตรวจ
- ใน audit คำถามตรง 5 ข้อเข้า DIRECT และตอบได้ทั้ง 5 ข้อ เช่น “เช็คอินกี่โมง” แต่ “เช็คอินได้ตั้งแต่กี่โมงครับ” เข้า RAG และถูกทิ้งคำตอบเพราะรูปแบบรหัส
- ชุด audit มีคำถามถอดความ คำถามที่ KB ไม่มีข้อมูล และคำถามท้าทายระบบ จึงไม่ได้แทนสัดส่วนคำถามที่ผู้ใช้ถามจริง

ดังนั้น **ยังสรุปไม่ได้ว่าระบบที่ผู้ใช้ทดสอบ fallback 76.4%** ต้องเทียบรุ่นที่รัน คำถาม และ log ของการทดสอบเดียวกันก่อน รายงานเดิมระบุขอบเขตเรื่องรุ่นโค้ดไม่ชัดพอ

คำที่ใช้ในรายงานนี้:

- **Fallback:** ข้อความสำรอง เช่น ขอให้แอดมินช่วยตรวจสอบ
- **RAG:** ค้นข้อมูลของร้าน แล้วให้ AI เรียบเรียงคำตอบจากข้อมูลนั้น
- **Vector:** การค้นด้วยความใกล้เคียงทางความหมาย
- **Classifier:** AI ที่ตัดสินว่าเป็นคำถามเกี่ยวกับธุรกิจ หรือคำถามทั่วไป

## 2. รอบแรก: แก้บั๊กการอ้างข้อมูล

| ก่อนแก้ | หลังแก้ |
| --- | --- |
| โมเดลส่ง `abc123` แต่โค้ดรอ `ANSWER_PATTERN:abc123` จึงทิ้งคำตอบ | ส่งป้าย `ref` ที่คัดลอกได้ตรง ๆ ให้โมเดล และรับ `abc123` ได้เมื่อชี้ไปยังข้อมูลที่เลือกเพียงรายการเดียว |
| Log บอกเหตุผลว่า `ANSWER` ทั้งที่คำตอบถูกปฏิเสธ | แยกเหตุผลว่า JSON ผิด หรืออ้างรหัสไม่ถูกต้อง |

รหัสที่ไม่มีอยู่ในข้อมูลที่ส่งให้โมเดล รหัสผิดแหล่ง หรือรหัสกำกวม ยังถูกปฏิเสธ การอ้างรหัสถูกต้องไม่ได้พิสูจน์ว่าเนื้อหาคำตอบถูกต้องทุกข้อ

## 3. รอบสอง: แก้อะไรเพิ่ม

| เรื่อง | ก่อนแก้ | พฤติกรรมปัจจุบัน |
| --- | --- | --- |
| **แยกคำถามทั่วไป** | ผลค้นด้วย vector อาจพาคำถามทั่วไปเข้า RAG แล้วจบที่แอดมิน | เมื่อผลหลักมีเพียง vector สนับสนุน จะถาม classifier ก่อน: ทั่วไป → ตอบทั่วไป, ธุรกิจ → ตอบจากข้อมูลที่ค้นได้, classifier ล้ม → แอดมิน |
| **การจัดอันดับข้อมูล** | คะแนนค้นคำจากข้อมูลสองชุดถูกนำมาเทียบกันตรง ๆ และคำทั่วไปก็ช่วยดันเอกสารขึ้นมา | จัดอันดับแต่ละชุดก่อนรวมผล; ตรงแค่คำทั่วไปหรือตัวเลขอย่างเดียวไม่นับว่ามีเนื้อหาเกี่ยวข้อง |
| **ข้อมูลที่ส่งให้ AI** | คำตอบซ้ำกินพื้นที่ และมีโอกาสเติมข้อมูล vector ที่ไม่เกี่ยวให้ครบ 3 รายการ | ตัดคำตอบเทียบเท่าของเรื่องเดียวกัน และไม่เติมข้อมูล vector ที่ไม่เกี่ยวเพียงเพื่อให้ครบจำนวน |
| **ข้อมูลเก่าและสถานะสด** | SNAPSHOT อาจถูกใช้ยืนยันว่าห้องยังว่าง | กันข้อมูลที่มี marker SNAPSHOT/ข้อมูลทดสอบ; ถอดกฎจับคำถามสถานะสดแบบเหมารวม คำถามจึงผ่าน retrieval ตามปกติ |
| **AI ล้มเหลว/งบหมด** | ตอบ fallback แต่บางเส้นทางไม่ได้ส่งเรื่องให้แอดมิน | ทุก AI fallback ทั้งข้อความและภาพ ส่งเรื่องให้แอดมินจริง ล้างบริบท AI แต่เก็บขั้นตอนสมัครสมาชิกไว้ และไม่ปิดการตอบ AI ของห้อง |
| **เลข 1/2/3** | พิมพ์ระหว่างตอบคำถามก็อาจกลายเป็นเลือกเมนู | ถอดเมนูเลข hard-code และ `allowLegacyDigits` ออกตามคำขอ ใช้ Rich Menu ที่กำหนดไว้; ตัวเลขเป็นข้อมูลในบทสนทนาหรือขั้นตอนสมัคร |
| **รูปแบบคำตอบ Gemini** | ขอ JSON ผ่านข้อความสั่งอย่างเดียว | เพิ่ม JSON schema ให้ Gemini ช่วยควบคุมรูปแบบ แล้วโค้ดยังตรวจคำตอบและรหัสอ้างอิงซ้ำ |

งานเล็กที่ทำพร้อมกัน:

- ปกปิดเบอร์โทร/บัญชี/รหัสผ่านตามกฎเดิม และเพิ่มอีเมล/เลข 13 หลัก ก่อนส่งข้อความหรือคำค้นให้ AI
- เพิ่มกฎใน prompt ว่า “ไม่ได้กล่าวถึง” ห้ามสรุปเป็น “ไม่มี”
- Error ที่มีคำว่า `aborted` เข้า retry เดิมได้
- ลบ log เมนูดิบและ session warning ที่ออกทุกข้อความ; เพิ่ม log ในทางออกที่เคยขาด
- เปลี่ยน template “ได้เลยค่ะ” เป็น “ได้เลยครับ”
- เพิ่ม schema ของคำตอบในรหัสสำหรับตรวจ request ซ้ำ เพื่อไม่หยิบผลของ request คนละรูปแบบมาใช้ซ้ำ ไม่ได้เปลี่ยนสูตรราคา/เครดิต

## 4. ไฟล์ classifier ที่เปิดอยู่ แก้อะไร

ใน [ai-intent-classifier.service.ts](../src/modules/chatbot/ai-intent-classifier.service.ts) เพิ่ม `failed: true` ในผลสำรองตอน classifier ทำงานไม่สำเร็จ

เดิมเมื่อ classifier ล้ม ระบบคืน `BUSINESS` เพื่อเลือกทางที่ปลอดภัย แต่หลังเพิ่มเส้นทางให้คำถามธุรกิจจาก vector ไป RAG ต้องแยกให้ออกว่า:

| ผล | ทำต่ออย่างไร |
| --- | --- |
| ตรวจสำเร็จ และเป็น BUSINESS พร้อมข้อมูลค้นคืน | เข้า RAG ได้ |
| ตรวจไม่สำเร็จ แต่คืน BUSINESS เป็นค่าปลอดภัย | ส่งต่อแอดมิน ห้ามถือว่าจำแนกสำเร็จ |

**ไฟล์นี้ไม่ได้เพิ่มการค้นข้อมูลหรือการตอบคำถามเอง** การตัดสินว่าจะเรียก classifier เมื่อไรอยู่ที่ [intent-router.service.ts](../src/modules/chatbot/intent-router.service.ts)

## 5. จุดที่เปลี่ยนพฤติกรรมและมีข้อแลกเปลี่ยน

| การเปลี่ยน | ผลที่ต้องรู้ |
| --- | --- |
| Classifier ก่อนตอบจาก vector | เส้นทางนี้อาจเพิ่ม AI call อีก 1 ครั้ง จึงอาจช้าหรือใช้เครดิตเพิ่ม |
| ถอดกฎจับสถานะสดก่อนค้น | คำถามเหล่านี้ผ่าน retrieval ตามปกติ แต่ยังไม่มี API ตรวจค่าปัจจุบัน; คำตอบ DIRECT ที่ผู้ดูแลเขียนไว้ส่งตรงได้ ต้องตรวจความสดของข้อมูลก่อนใช้ตอบตัวเลข |
| กรอง/ลดข้อมูลก่อนส่ง AI | อาจช่วยลดข้อมูลรบกวน แต่ก็อาจทำให้บางคำถามหลายประเด็นได้หลักฐานน้อยลง ต้องวัดกับ KB จริง |
| Prompt ห้ามอนุมานเอง | ช่วยกำกับโมเดล แต่ยังรับรองไม่ได้ว่าโมเดลจริงจะทำตามทุกครั้ง |

**จึงยังบอกไม่ได้ว่า fallback หลังแก้เหลือกี่เปอร์เซ็นต์** ยังไม่มีการรันชุดคำถามเดิมกับโมเดลจริงหลังแก้ และไม่ควรตีความว่า fallback ทุกครั้งเป็นข้อผิดพลาด

## 6. สถานะงานและผลทดสอบ

| รายการ | สถานะ |
| --- | --- |
| บั๊ก ref รอบแรก | อยู่ใน checkpoint ปัจจุบันแล้ว |
| การแก้รอบสอง | ยังอยู่ใน working tree ยังไม่ commit ณ ตอนตรวจรายงานนี้ |
| Deploy โดยผู้ช่วย | ยังไม่ได้ทำ |
| Dependency / ตารางฐานข้อมูล / migration ใหม่ | ไม่มี |
| เปลี่ยนข้อมูล KB ในฐานข้อมูล | ไม่ได้ทำ; SNAPSHOT ถูกกรองขณะค้น/ตอบ |
| ทดสอบทั้ง repo รอบแก้ล่าสุด | ผ่าน 444 ข้อ, ล้ม 17 ข้อเดิมใน billing/pricing, skipped 5 |
| TypeScript / lint ไฟล์ที่แก้ / build | ผ่านในรอบแก้ล่าสุด |
| โมเดลสด / LINE จริง หลังแก้ | ยังไม่ได้ทดสอบ |

ตัวเลขทดสอบเป็นผลจากรอบแก้ก่อนหน้า วันที่จัดทำรายงานนี้ตรวจโค้ดและสถานะไฟล์ ไม่ได้รันทดสอบใหม่

## 7. อะไรใน audit ที่ยังไม่ได้แก้

- การเรียงข้อความข้าม worker หลาย instance
- การกันบันทึก postback ซ้ำและ cache เมนูข้าม instance
- การตรวจ payload/ความยาวข้อความ LINE และ sticker routing บางกรณี
- Billing/pricing tests เดิมที่ยังล้ม 17 ข้อ
- ระบบวัด fallback จากการใช้งานจริงและการประเมินคุณภาพหลังแก้ด้วยโมเดลจริง

ก่อน deploy ต้องจัดการ turn ที่ค้างให้จบด้วย worker รุ่นเดิม เพราะ prompt/schema ที่เปลี่ยนมีผลต่อรหัส request สำหรับ replay

หลักฐานละเอียดและคำสั่งทดสอบอยู่ใน [รายงานตรวจสอบเดิม](chatbot-fallback-verification-2026-09-27.md)
